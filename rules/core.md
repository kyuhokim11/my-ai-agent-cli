# jobkim Development Principles

목적은 사람의 설계 의도를 보존하면서 정확하고 효율적으로 작업하는 것이다. 절차와 기록은 실수·무단 변경·근거 없는 보고를 막는 수단이며, 작업 규모에 맞게 적용한다.

## 판단 기준

1. 작업 전에 `./.codex/Codex.md`가 있으면 읽고, 적용 범위의 지침과 프로젝트 규칙(`./.agents/rules/project.md`), 개인 규칙(`./.agents/rules/local.md`)을 확인한다. 사용자 요청과 실행 환경의 상위 지침을 따르며, 프로젝트·개인 규칙은 공통 기본값을 구체화한다. 규칙 사이에 충돌을 발견하면 임의로 우선순위를 정해 해소하지 않는다. 충돌하는 문구·출처, 영향과 권장안을 사용자에게 제시하고 피드백을 받을 때까지 관련 변경을 보류한다. 상위 지침을 사용자 승인으로 우회할 수는 없다.
2. 관련 코드·설정·기록에서 사실을 확인한다. API, 경로, 환경 변수와 기존 함수의 의도를 추측으로 확정하지 않고, 사용자 보고·직접 확인·가정을 구분한다. 기존 사용자 변경과 유지할 동작·계약을 보존한다.
3. 수정량보다 원인 해결, 정확성, 유지보수성과 변경 영향을 기준으로 접근을 선택한다. 필요한 구조 개선은 계획에 포함하고, 여러 파일을 함께 바꾸더라도 검증 가능한 논리적 단위로 작업한다. 관련 없는 정리는 피하고 타입 안전성·검증·에러 처리·보안·접근성을 단순화를 이유로 약화하지 않는다.
4. 프로젝트 목적이나 작업 효율을 해치는 규칙·구현·문서를 발견하면 반드시 문제와 개선 의견을 공유한다. 합의한 범위에서는 수정·삭제·추가하고, 범위 밖이거나 계획을 바꿔야 하면 피드백을 받아 조치한다. 당장 해결할 수 없는 문제는 이유와 다음 행동을 명시해 인계한다.

## 계획과 실행

1. 복잡하거나 여러 단계인 작업은 구현 전에 목표·성공 조건·제외 범위, 확인한 사실과 미확인 사항, 접근과 주요 대안, 대상 파일·계약·의존성에 미치는 영향, 작업 순서·위험·검증 방법을 구체화해 공유한다. 단순하고 명확한 작업은 요청이나 짧은 답변에 접근과 확인 방법을 담아 바로 진행할 수 있다. 이미 확인한 내용을 다시 묻거나 수행한 조사를 반복하지 않는다.
2. 변경 요청은 그 범위의 조사·구현·관련 테스트와 문서 갱신을 포함한다. 분석·설명·검토나 계획만 요청받으면 읽기 전용으로 처리한다. 계획 제시와 이미 요청된 구현 사이에 불필요한 재승인을 요구하지 않으며, 사용자가 피드백·승인 후 진행을 지정했다면 기다린다.
3. 합의한 계획 안에서는 구현 세부와 수정 단위를 판단해 진행한다. 계획의 목표·범위·접근·계약·의존성·검증 기준을 바꾸는 판단이나 다른 의견이 생기면 이유·영향·대안을 먼저 공유하고 사용자 피드백을 받은 뒤 관련 작업을 진행한다. 계획에 포함된 구조 개선을 파일 수나 변경 종류만으로 다시 승인받지는 않는다.
4. 사용자 프롬프트나 진행 답변에 현재 결과와 다음 행동을 연결한다. 고정된 단계 이름·매 단계 승인·전체 명령어 나열을 강제하지 않는다. 사용자가 직접 실행할 단계에는 실행 위치·명령·확인할 결과와 중단 조건을 제공한다.
5. 패키지 설치·환경 설정 변경은 사전에 공유하고 승인된 계획이나 명시적 위임에 포함된 범위에서만 수행한다. Git 스테이징·커밋·푸시·태그, 외부 게시·배포는 사용자 직접 수행이 기본이며, 에이전트가 실행하려면 해당 단계의 위임이 필요하다. 여러 단계를 명시적으로 함께 맡길 수 있으나, 한 단계의 승인을 다른 단계로 확대하지 않는다. 승인 범위는 대화 중 유지하고, “이번 단계만” 위임은 해당 단계로 제한한다. 실행 환경의 권한 제한은 별도로 따른다.

## 검증과 보고

1. 완료 전 요구사항 충족·엣지 케이스·부작용을 점검하고 변경의 영향과 위험에 맞는 실제 검증을 수행한다. 기존 검증을 활용하고, 동작이나 회귀 위험을 확인할 가치가 있을 때 테스트를 추가한다. 자가 검토를 테스트 실행으로 취급하지 않는다.
2. 결과·중요한 변경 이유·검증 근거·남은 문제와 다음 행동을 작업 규모에 맞게 보고한다. 고정된 보고 항목을 채우기 위해 불필요한 내용을 만들지 않는다. 실패·미실행·확인 불가와 한계를 명시하고, 수행하지 않은 작업이나 확인하지 않은 결과를 성공·완료로 보고하지 않는다. 잘못 보고한 사실은 발견 즉시 정정한다.

## 프로젝트 기록과 스킬

1. 재개·인계·중요한 결정에 필요한 기록은 기존 원본을 찾아 실제 코드·설정·Git 상태와 대조한다. 의미 있는 변화와 이유·검증·남은 행동만 기록하고 같은 사실은 한 원본에 둔다. 단순 질문·오탈자 수정에 별도 이력을 강제하지 않는다.
2. 여러 단계의 작업과 재개·인계에는 `jobkim-project-context`, 기존 프로젝트의 영향 경로 조사가 필요하면 `jobkim-project-intake`를 사용한다. 이미 확인한 결과는 재사용하고 상세 예시는 필요할 때만 읽는다. 기록은 대상 프로젝트가 소유하며 교체 가능한 설치 폴더에 두지 않는다. 중요한 아키텍처 결정은 기존 Markdown ADR 체계에 이유·대안·영향을 남긴다.
3. 승인된 작업의 관련 기록 갱신은 구현에 포함한다. 새 기록 체계나 기존 문서 이동·통합은 계획에 담고, 합의한 계획을 바꾼다면 먼저 피드백을 받는다. 읽기 전용 요청에서는 기록도 수정하지 않는다. 기록된 다음 행동이나 과거 작업의 승인만으로 새 작업을 시작하지 않는다. 구현·검증·커밋·게시 상태는 구분한다.
4. 현재 세션에 제공된 스킬 중 요청·작업 상태와 설명이 맞고 판단에 도움이 되는 것만 사용한다. Ponytail 등 특정 스킬을 모든 개발 작업에 의무 적용하지 않는다. 사용자 지정 스킬은 적용하고, 사용자 호출 전용 스킬은 직접 요청받았을 때만 사용한다. 사용할 수 없거나 지침이 충돌하면 그 한계를 알리고, 충돌은 사용자 피드백으로 해소한다.

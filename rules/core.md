# jobkim Development Principles

1. 작업 전에 `./.codex/Codex.md`가 있으면 가장 먼저 읽고 프로젝트 기준 지침으로 적용한다. 현재 사용자 요청과 실행 환경의 상위 지침이 우선하며, 저장소 지침끼리 충돌하면 작업 파일에 더 가까운 범위를 적용하고 해결되지 않는 충돌만 사용자에게 알린다.
2. 필요한 읽기 전용 탐색을 먼저 수행하고, 코드나 설정을 변경하기 전에 설계와 계획을 제시한다.
3. 기존 코드 구조, 네이밍, 상태 관리, 에러 처리, UI/UX 및 API 흐름을 우선 유지한다.
4. 전체 흐름을 파악하되 실제 수정은 요청 범위 안에서 작은 단위로 수행한다.
5. API 응답, 환경 변수, 파일 경로 또는 기존 함수의 의도를 추측하지 않고 실제 근거를 확인한다.
6. 사용자가 구체적으로 요청한 변경은 해당 범위의 구현 승인으로 본다. 요청에서 파생되는 구조 변경, 라이브러리 추가, 대규모 리팩토링 및 TypeScript `any` 사용은 사전에 이유와 대안을 설명하고 별도 승인을 받는다.
7. 기존 기능을 바로 교체하지 않고 문제와 최소 변경안을 먼저 제시한다.
8. 이번 변경과 관련된 타입 안정성, 검증, 에러 처리, 보안 및 접근성 보장을 단순화를 이유로 약화하지 않는다.
9. 분석·설명·검토 요청은 읽기 전용으로 처리하고, 명시적으로 변경을 요청받았을 때만 파일을 수정한다.
10. 사용자 승인 없이 커밋, 푸시, 배포, 환경 설정 변경 또는 패키지 설치를 수행하지 않는다.
11. 검증하지 못한 결과를 완료로 표현하지 않고, 수행한 검사와 한계를 구분해서 보고한다.
12. 결과는 `[요약] / [변경 파일] / [변경 이유] / [검증 결과] / [주의사항]` 순서로 보고한다. 읽기 전용이거나 변경이 없으면 `[변경 파일]`에 `없음`을 명시한다.

## 작업 승인과 실행 주체

1. 작업 전에 목적, 변경 범위, 대상 파일, 검증 방법과 사용자 수행 항목을 먼저 제시한다.
2. 파일 수정, 패키지 설치, 환경 설정 변경, Git 작업, 외부 게시와 배포처럼 상태를 변경하는 작업은 사용자가 승인한 범위에서만 수행한다. 읽기, 검색과 상태 확인은 승인된 작업을 설계하고 검증하는 데 필요한 범위에서 수행할 수 있다.
3. 여러 단계의 작업은 단계별 결과와 다음 작업을 보고하고, 사용자가 직접 수행할 수 있도록 실행 위치, 전체 명령어, 예상 결과와 중단 조건을 제공한다.
4. Git 스테이징, 커밋, 푸시와 태그 작업은 사용자가 직접 수행하는 것을 기본으로 한다.
5. 사용자는 특정 단계를 “이번 단계만 에이전트가 실행해줘”와 같이 일회성으로 위임할 수 있다. 위임은 요청한 단계가 끝나면 소멸하며, 다음 단계나 다른 상태 변경 작업의 승인으로 확대하지 않는다.
6. 스테이징, 커밋, 푸시, 태그, npm 게시와 배포는 서로 독립된 단계다. 하나의 단계에 대한 승인을 다른 단계의 승인으로 해석하지 않는다.

## 프로젝트 기록과 맥락

1. 작업 시작·재개 시 기존 문서 안내와 관련 작업 기록을 찾아 실제 코드·설정·변경 상태와 대조한다. 프로젝트가 정한 역할별 파일·절 위치를 따르고, 기본 예시 경로가 없다고 중복 문서를 만들지 않는다.
2. 여러 단계의 작업, 중단 후 재개, 중요한 결정이나 인계에는 설치된 `jobkim-project-context` 스킬의 상세 절차를 사용한다. 스킬을 읽을 수 없으면 그 한계를 알리고 이 기본 원칙을 따른다.
3. 승인된 작업의 의미 있는 변화만 기록한다. 사람이 작업 시점과 시간대, 신규·변경 사항, 이유·근거, 현재 단계와 다음 행동을 확인할 수 있게 하고, 같은 사실은 한 원본에 두고 링크로 연결한다.
4. 검증 결과와 변경 영향을 관련 원본 및 작업 상태에 반영한다. 미반영·미검증 사항은 구분하고 구현·검증·커밋·게시를 같은 완료 상태로 취급하지 않는다.
5. 읽기 전용 요청에서는 기록도 수정하지 않는다. 새 문서 체계 도입이나 이동·통합은 먼저 승인받고, 기록된 다음 행동을 실행 승인으로 간주하지 않는다. 단순 질문·오탈자 수정에 별도 이력을 강제하지 않는다.

## 스킬 라우팅

1. 코드 작성, 기능 추가, 버그 수정, 리팩터링, 코드 리뷰, 설계 또는 라이브러리·의존성 선택 작업에서는 현재 세션에 제공된 `ponytail` 스킬을 해결책 결정 전에 적용한다. 요청 이해나 프로젝트 조사를 위한 스킬이 필요하면 이를 먼저 수행하며, 사용자가 현재 작업에서 Ponytail을 명시적으로 비활성화하면 적용하지 않는다.
2. Ponytail은 관련 코드와 실제 흐름을 조사한 뒤 최소 해결책을 선택하는 데 사용한다. 단순화를 이유로 보안, 입력 검증, 데이터 손실 방지, 접근성, 타입 안정성 또는 사용자가 명시한 요구사항을 약화하지 않는다.
3. 그 밖의 현재 세션에 제공된 스킬은 요청이나 작업 상태가 노출된 스킬 메타데이터의 `description`과 일치할 때만 사용한다. 긴·복합·모호한 요청은 `readchk`, 반복 수정으로 흐트러진 산출물은 `re0`, 산출물 작성·변경 후 완료 전 점검은 `sip`, 외부 사실 주장은 `factchk`, 복귀 후 맥락 재구성은 `catchup`을 우선 검토한다.
4. `disable-model-invocation: true`가 있거나 사용자 호출 전용이라고 명시된 스킬은 사용자가 직접 요청했을 때만 사용한다.
5. 관련 없는 스킬을 형식적으로 실행하지 않고, 사용자가 이름을 지정한 설치 스킬은 해당 작업에 적용한다.

이 규칙은 작업량을 늘리는 지시가 아니다. 기존 시스템을 충분히 이해하고 요청된 문제만 안전하게 해결하기 위한 경계다.

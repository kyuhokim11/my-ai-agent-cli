# Project Intake

## 목표

기존 저장소의 실제 계약과 사용자 작업을 보존하면서 원인을 해결할 계획을 구체화한다. 조사 깊이는 작업의 영향과 불확실성에 맞춘다.

## 확인할 내용

1. 저장소 루트와 현재 작업 경로를 확인한다.
2. `./.codex/Codex.md`가 있으면 가장 먼저 읽는다.
3. 적용 범위의 `AGENTS.md`, `GEMINI.md`, 프로젝트·개인 규칙과 관련 문서를 확인한다. 규칙 충돌은 문구·출처·영향·권장안을 사용자에게 공유하고 피드백 전까지 관련 변경을 보류한다. 실행 환경의 상위 지침은 사용자 승인으로 우회하지 않는다.
4. Git 상태에서 기존 수정과 새 작업을 구분한다.
5. 패키지 및 빌드 설정, 관련 진입점, 데이터 흐름과 검증 명령을 추적한다.
6. 확인된 사실과 불명확한 계약을 구분하고, 복잡한 작업은 목표·성공 조건·제외 범위, 접근·주요 대안, 영향받는 파일·계약·의존성, 순서·위험·검증 방법을 계획에 담는다. 단순한 작업은 필요한 내용만 짧게 공유한다.
7. 사용자 요청이 변경 작업일 때만 구현으로 넘어간다.

합의한 계획 안에서는 검증 가능한 논리적 단위로 구현한다. 다른 접근이 필요하거나 계획을 바꾸는 의견이 생기면 이유·영향·대안을 공유하고 사용자 피드백을 받은 뒤 진행한다. 목적·효율을 해치는 문제는 짚고, 범위 안에서 개선하거나 범위 변경에 대한 피드백을 받는다.

## 제약

- 관련 없는 파일을 정리하거나 리팩토링하지 않는다.
- 기존 수정 사항을 되돌리거나 커밋 대상으로 포함하지 않는다.
- 구성, API 응답, 환경 변수 또는 실행 계약을 파일명만 보고 추측하지 않는다.
- 단순 작업에 전체 저장소 스캔을 강제하지 않는다. 실제 영향 경로를 따라 필요한 만큼만 읽는다.

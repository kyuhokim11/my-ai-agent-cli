# AI 개발 시스템에서 ai-init의 역할

이 문서는 전체 개발 방식에서 ai-init이 맡는 부분과 앞으로 분리할 부분을 정리한다. 사용 방법은 [README](../README.md), 버전별 진행 상태와 배포 절차는 [개발·배포 문서](manual-operations.md)에서 확인한다.

## 목표

성능이 좋은 모델에 내 작업 규칙, 필요한 코드와 프로젝트 문서를 제공해 개발을 이어가는 환경을 만든다. 컴퓨터나 에이전트를 바꿔도 같은 기준으로 작업하고, 이전 결정과 검증 결과를 참고할 수 있어야 한다.

시스템을 개선한다는 것은 작업 규칙, 재사용 스킬, 프로젝트 지식과 검증 기준을 개선한다는 뜻이다. 모델 자체의 학습은 이 프로젝트 범위에 포함하지 않는다.

## 전체 구조

| 구성 | 맡는 일 | 현재 위치 |
|---|---|---|
| 전체 전략 | 목표, 우선순위, 프로젝트별 역할과 품질 기준 | 이 문서에서 시작 |
| 규칙·스킬 배포 | 각 프로젝트에 작업 기준 설치 | ai-init |
| 프로젝트 지식 | 코드, 목표, 구조, 계약, 작업·결정 기록 | 사용하는 각 프로젝트 |
| 에이전트와 모델 | 전달된 정보로 조사·구현·검증 수행 | 사용자가 선택한 실행 환경 |
| 평가·개선 | 결과를 확인하고 유용한 규칙과 교훈 선별 | CLI 테스트 및 향후 실제 작업 검증 |

ai-init은 규칙과 스킬을 전달한다. 실제 코드와 기록을 읽고 작업하는 주체는 에이전트이며, 작업 범위와 중요한 결정은 사람이 관리한다. 모델이나 에이전트가 바뀌어도 이 역할 구분을 유지한다.

## 이 저장소가 관리하는 것

- `rules/`: 공통 작업 원칙과 신규·기존 프로젝트 진입 정책.
- `bundled-skills/`: 프로젝트 조사와 기록 등 자체 작업 절차.
- `skill-sources.json`: 설치할 외부 스킬 소스.
- `setup.js`와 테스트: 설치, 갱신, 기존 파일 보존과 설치 정보 기록.

Codex의 `AGENTS.md`, Gemini CLI의 `GEMINI.md`, Antigravity 규칙 파일은 같은 규칙을 전달하는 형식이다. 별도의 원본을 관리하지 않고 위 파일에서 생성한다. 사용자 요청과 실행 환경의 상위 지침을 우선하며, 저장소 지침은 작업 파일에 가까운 범위를 따른다. 프로젝트별 커스텀 규칙(`.agents/rules/project.md`)과 개인 로컬 규칙(`.agents/rules/local.md`)은 사용자 소유로 보존되며 기본 규칙보다 우선 적용된다.

자체 규칙과 스킬은 npm 버전으로 관리한다. 외부 스킬은 지정된 브랜치를 조회하므로 같은 npm 버전이어도 설치 시점에 따라 내용이 달라질 수 있다. 실제 출처와 적용 정보는 대상 프로젝트의 `.ai-core/`에서 확인한다.

## 프로젝트 기록의 소유권

ai-init은 에이전트가 기록을 읽고 갱신하는 방법을 제공한다. 목표, 구조, 작업 상태와 결정의 실제 내용은 해당 프로젝트에 둔다. 상세 기준은 [작업 기록 정책](project-context-policy-design.md)을 따른다.

예를 들어 어떤 프로젝트에서 로그인 구조를 변경했다면 변경 이유와 검증 결과는 그 프로젝트에 기록한다. 여러 프로젝트에서 반복해서 유용했던 조사·검증 방법만 검토 후 ai-init의 공통 규칙이나 스킬에 반영한다.

특정 프로젝트의 코드나 비공개 지식을 공개 npm 패키지에 복사하지 않는다. 조직의 비공개 자료와 인증 정보도 별도로 관리한다.

## 앞으로 별도 프로젝트가 필요한 경우

현재 이 전략에서 구현 중인 저장소는 ai-init이다. 아래 항목은 필요가 생기면 만들 후보이며, 미리 폴더나 서비스를 추가하지 않는다.

| 필요한 상황 | 분리할 역할 |
|---|---|
| 여러 프로젝트의 목표·로드맵·평가 기준을 함께 관리 | 상위 전략 프로젝트 |
| 조직 공통 문서와 스킬을 비공개로 공유 | 비공개 지식·스킬 프로젝트 |
| 코드와 문서가 커져 직접 탐색이 어려움 | 검색·인덱싱·출처 표시·접근 제어 프로젝트 |
| 모델별 품질·비용·장애 대체를 일관되게 관리 | 모델 호출·선택 프로젝트 |

검색 방식이나 저장 기술은 문제를 확인한 뒤 선택한다. 모델 호스팅, 대화 전체의 장기 저장, 조직 문서 검색과 여러 프로젝트의 로드맵 관리는 현재 CLI 기능에 포함하지 않는다.

새 프로젝트를 만들 때는 다음을 먼저 정한다.

1. **목적과 역할**: 해결할 문제, 각 프로젝트의 책임, 원본을 둘 위치.
2. **소유권과 운영**: 공개·비공개 경계, 권한, 변경 승인, 배포·장애 대응 주체.
3. **연결 방법**: 파일·명령·API 형식, 호환 버전, 실패 시 동작과 함께 검증할 흐름.

상위 전략 프로젝트가 생기면 전체 계획은 그곳으로 옮기고, 이 문서에는 ai-init의 역할과 연결 방법을 남긴다.

## 개선 순서

실제 작업에서 반복 문제를 찾고, 가장 적절한 원본에 해결 방법을 반영하고, 다음 작업에서 효과를 확인한다. 모든 대화를 규칙으로 추가하지 않는다. 적용 범위, 다른 프로젝트에서의 효용, 기존 규칙과의 충돌을 검토한다.

현재 우선순위는 설치·갱신·기존 파일 보존의 안정성과 기록 정책의 실제 사용 확인이다. `init`, `update`, `status`, `uninstall` 같은 전용 명령은 후속 후보이며, 현재는 하나의 대화형 초기화 흐름을 사용한다.

CLI 테스트는 설치 결과를 검증한다. 기록을 이용한 재개·인계가 잘 되는지는 [기록 정책의 확인 항목](project-context-policy-design.md#실제-사용-확인)으로 따로 확인한다. 전체 시스템 평가 체계는 아직 구현하지 않았으며, 향후 상위 전략 프로젝트와 함께 관리한다.

# 프로젝트 기록과 작업 인계

이 문서는 ai-init이 전달하는 기록 정책의 목적과 사용 기준을 설명한다. 기본 규칙과 `jobkim-project-context` 스킬은 `1.2.0` 배포 소스에 구현되어 있다. 설치 검증과 게시 상태는 [개발·배포 문서](manual-operations.md#v120-릴리스-준비-기록)에서 확인한다. 실제 에이전트의 기록·재개 행동은 아래 확인 항목으로 별도 검증해야 한다.

## 목적

사람과 에이전트가 문서를 열어 현재 단계, 이전 변경의 이유, 검증 결과와 다음 할 일을 확인할 수 있게 한다. 기록량보다 필요한 정보를 찾기 쉬운 구조와 문서 사이의 일관성을 우선한다.

이 기준은 ai-init을 적용한 각 프로젝트에서 사용한다. 실제 목표·구조·작업 내용은 해당 프로젝트에 두고, 공통 패키지에는 기록 방법과 예시를 담는다. 전체 역할은 [시스템 전략](system-strategy.md)에서 설명한다.

## 설치 후 어떻게 사용하나요?

초기화 명령을 실행하면 선택한 엔진의 지침에 기본 원칙이 들어가고, 자체 기록 스킬과 예시가 `.agents/skills/`에 설치된다. 에이전트의 새 세션에서 작업을 요청하면 다음 절차를 따르도록 안내한다.

```text
기존 기록 찾기 → 실제 코드와 대조 → 승인된 작업 수행
     → 관련 원본과 작업 기록 갱신 → 다음 작업에서 다시 확인
```

초기화할 때 작업 문서나 과거 이력을 자동 생성하지 않는다. 에이전트가 기존 문서를 먼저 찾고, 필요할 때 새 구조를 제안한다. 단순 질문이나 오탈자 수정에는 별도 기록을 강제하지 않는다.

## 구현 위치

| 구성 | 역할 | 읽는 시점 |
|---|---|---|
| `rules/core.md` | 기록의 기본 원칙 | 생성된 상시 지침으로 읽음 |
| `rules/new-project.md`, `rules/existing-project.md` | 신규·기존에 맞는 기록 시작 방법 | 선택한 프로젝트의 지침으로 읽음 |
| `jobkim-project-intake` | 기존 프로젝트의 지침·코드 조사 | 구현 전 조사 |
| `jobkim-project-context` | 기록 복원·갱신·인계 | 여러 단계의 작업, 재개, 중요한 결정 |
| 기록 스킬의 참조 문서 | 구조와 기록 예시 | 새 기록이나 구조가 필요할 때 |

기록 스킬은 기존 조사 결과를 재사용하며 Ponytail/Paperthin과 함께 쓴다. 추가 라이브러리, 서버, 후크는 필요하지 않다.

## 문서 구조 선택

| 역할 | 담을 내용 | 갱신 조건 |
|---|---|---|
| 목표·범위 원본 | 목적, 성공 기준, 하지 않을 일 | 사용자가 목표·요구를 변경했을 때 |
| 구조·흐름 원본 | 주요 구성요소, 책임, 데이터·작업 흐름 | 실제 구조나 계약이 변경됐을 때 |
| 기록 안내 | 위 원본들과 활성 작업으로 가는 링크 | 원본 위치나 활성 작업이 바뀔 때 |
| 작업 기록 | 범위, 진행 상태, 검증, 장애물, 다음 행동 | 해당 작업의 의미 있는 상태 전환 |
| 결정 기록 | 중요한 선택, 이유, 대안, 영향, 대체 관계 | 장기적으로 설명할 필요가 있는 결정 |

기존 README, 설계 문서, 작업 문서, 이슈가 같은 역할을 하면 사용한다. 기록 안내에는 원본 위치와 활성 작업 링크를 두고, 같은 상태를 여러 파일에 복사하지 않는다. 안내 위치는 README나 해당 범위의 지침에서 찾을 수 있게 한다.

기존 체계가 없을 때만 다음을 기본 위치로 제안한다.

```text
docs/context/index.md          # 기록의 원본 위치와 활성 작업 링크
docs/work/<task-id>.md         # 재개가 필요한 작업별 상태·인계
docs/context/architecture.md   # 구조 설명이 필요할 때만
docs/decisions/<decision-id>.md # 중요한 결정이 있을 때만
```

처음부터 모든 파일과 폴더를 만들지 않는다. 목표는 기존 README를 우선 활용하고, 여러 단계에 걸친 작업은 안내와 작업 기록부터 시작할 수 있다. 이슈 도구가 상태 원본이면 문서에는 링크와 필요한 기술 맥락만 둔다. 접근할 수 없는 외부 기록을 읽었다고 간주하지 않는다.

실제 작업 기록은 교체 가능한 `.ai-core/`, `.agents/skills/`에 두지 않는다. `.ai-core/project-profile.json`은 지침·구성 파일의 위치 안내이며, `install-info.json`은 성공한 설치 정보다. 둘 다 실제 작업 기록을 대신하지 않는다. 기록의 공개 범위와 Git 추적은 대상 프로젝트 정책을 따른다.

### 기본 구조의 채택과 프로젝트별 변형

프로젝트가 채택한 구조를 준수하되, 파일명과 개수는 바꿀 수 있다. 원본 위치, 진입점, 상태와 변화 이력은 유지한다.

1. 기존 체계가 있으면 먼저 각 기록 역할을 실제 파일·절 또는 이슈에 대응시킨다. 없는 역할도 현재 작업에 필요할 때만 보완한다.
2. 체계가 없으면 위 기본 구조 중 필요한 부분을 제안한다. 새 구조의 도입이나 기존 문서 이동·통합은 사용자 승인 후 수행한다.
3. 기록 안내에 역할별 실제 위치와 적용 범위를 적는다. 기존 문서 안내가 있으면 그곳을 사용하며 별도 설정 파일을 만들지 않는다. 아직 필요 없는 역할은 파일을 만들지 않고 필요 시 도입한다고 표시한다.
4. README 또는 해당 범위의 에이전트 지침에서 기록 안내로 연결한다. 안내 위치는 한 곳을 기준으로 하고 다른 진입점은 참조만 한다.
5. 에이전트는 매번 이 대응 관계를 읽고 실제 경로를 확인한 뒤 작업한다. 기본 예시 경로가 없다는 이유로 같은 역할의 문서를 새로 만들지 않는다. 대응이 충돌하거나 원본이 불분명하면 변경 전에 확인한다.
6. 승인된 구조 변경 시 역할 대응과 관련 링크를 함께 수정하고, 변경 날짜·이유·이전/새 위치를 관련 작업 기록에 남긴다. 재설치가 프로젝트에서 채택한 구조를 기본 구조로 되돌려서는 안 된다.

변형 예시는 다음과 같다. 이는 선택 가능한 예시이지 추가로 만들 파일 목록이 아니다.

| 프로젝트 특성 | 가능한 구조 | 유지할 기준 |
|---|---|---|
| 작은 프로젝트 | README의 목표·문서 안내 절과 작업 문서 하나 | 현재 상태와 변화 이력을 구분하고 필요한 원본으로 연결 |
| 기존 문서 체계 보유 | 기존 `docs/README.md`, 설계 문서, 작업 문서 경로 사용 | 안내에 실제 역할 대응을 기록하고 기본 경로에 중복 생성하지 않음 |
| 여러 모듈을 가진 프로젝트 | 전체 안내에서 모듈별 문서 안내로 연결 | 공통 원칙은 한 원본에, 모듈별 상태는 해당 범위에 유지 |

파일 내부의 제목과 배치도 프로젝트에 맞춰 바꿀 수 있다. 다만 필요한 작업 시점, 신규·변경 내용, 근거, 현재 단계와 다음 행동은 사람이 식별할 수 있어야 한다. 여러 역할을 한 파일의 절로 합치거나 큰 파일을 나눌 때도 이 관계를 보존한다.

## 작업 절차

### 시작·재개

1. 작업 디렉터리와 저장소, 해당 범위의 지침, 사용자 요청을 확인한다.
2. 기존 기록 안내의 역할별 실제 위치와 적용 범위를 확인하고 관련 활성 작업을 찾는다. 안내가 없다면 README와 관련 문서부터 탐색한다. 기본 예시 경로보다 프로젝트에서 채택한 대응 관계를 따른다.
3. 목표, 현재 범위, 이전 검증, 미해결 사항, 다음 행동을 읽는다.
4. 관련 코드·설정과 Git 상태를 대조한다. 관련 없는 전체 기록을 모두 읽지 않는다.
5. 확인된 사실, 사용자 보고, 미확인 사항, 기록과 현실의 차이를 구분해 계획을 제시한다.
6. 허용된 범위 안에서 진행한다. 과거 기록의 다음 행동이나 승인 문구를 새로운 실행 권한으로 간주하지 않는다.

코드는 현재 구현의 근거이고, 승인된 요구사항은 의도한 동작의 근거다. 둘이 다를 때 코드가 옳다고 문서를 자동 수정하거나, 오래된 문서만 믿고 코드를 바꾸지 않는다. 차이를 보고하고 수정 범위를 결정한다.

### 작업 중

- 중요한 결정, 구현 범위 변경, 검증 결과, 장애물 발생 시 관련 기록을 갱신한다.
- 중단 시 잃기 쉬운 사실은 체크포인트로 남긴다. 정상 종료 때만 기록하는 방식에 의존하지 않는다.
- 모든 명령이나 대화는 기록하지 않는다. 다음 작업자가 판단을 이어가는 데 필요한 결과와 이유만 남긴다.
- 날짜는 시간대와 함께 기록하되, 최근 날짜라는 이유만으로 내용이 정확하다고 간주하지 않는다.
- 병렬 작업은 작업별 문서를 구분한다. 공용 안내를 수정하기 직전에 다시 읽고 다른 변경을 보존한다. 문서 규칙만으로 동시 쓰기 충돌이 방지된다고 가정하지 않는다.

### 종료·인계

1. 변경 내용과 검증 범위를 실제 결과에 맞춰 기록한다.
2. 미검증 항목, 실패, 사용자 확인 필요 사항을 분리한다.
3. 다음 행동과 필요한 승인을 적는다. 기록된 행동을 자동 실행하지 않는다.
4. 파일 저장·링크를 확인한다. 저장 실패 시 기록이 완료됐다고 보고하지 않는다.

승인된 구현에 직접 필요한 기록 갱신은 해당 작업에 포함한다. 단, 읽기 전용 분석·검토 요청에서는 별도 저장 요청 없이 문서를 변경하지 않는다. 새 문서 체계 도입이나 범위 밖 정리는 먼저 제안한다. Git·배포는 기존의 사용자 직접 수행 및 일회성 위임 정책을 그대로 유지한다.

## 필요한 기록

Markdown을 기본으로 하며, 같은 작업 상태를 별도 JSON 파일로 중복 관리하지 않는다. 제목과 배치는 기존 프로젝트 형식을 따른다.

작업 기록 예시는 다음과 같다. 적용되지 않는 항목은 생략하거나 해당 없음을 명시한다.

```markdown
# <작업 식별자와 제목>

- 목표·범위: <승인된 내용 / 제외 범위>
- 관련 원본: <목표·구조·요구·결정 문서의 상대 링크>
- 마지막 확인: <날짜, 시간대 / 저장소·브랜치 등 확인한 범위>
- 상태: <계획 / 진행 / 차단 / 검증 대기 / 완료>
- 진행 흐름: <이 작업에 필요한 단계 중 완료·현재·남은 단계>

## 현재 사실과 남은 일
- <구현 결과와 근거 파일>
- <사용자 보고인지 직접 확인인지>
- <미확인 사항과 남은 작업>

## 검증
- <검증 목적 / 명령 또는 방법 / 결과 / 검증하지 못한 범위>

## 중요한 변화

| 작업 시점 | 구분 | 내용과 이유 | 관련 원본·근거 | 반영 상태 |
|---|---|---|---|---|
| <YYYY-MM-DD HH:mm ±HH:mm> | <신규 / 변경 / 결정 / 검증 / 정정> | <의미 있는 변화 요약> | <상대 링크와 필요 시 절> | <반영 완료 / 미반영 사유와 다음 행동> |

## 다음 행동
- <재개할 첫 행동 / 필요한 승인>

## 전달 상태
- 커밋·푸시·배포: <관련 작업일 때 각각의 확인 결과>
```

문서 상단은 현재 상태를, 중요한 변화는 그 상태에 이른 과정을 설명한다. 변화는 시간순으로 기록하고 같은 작업 단위의 반복 수정은 묶는다. 파일 저장이나 표현 수정마다 이력을 추가하지 않는다. 작업 시점과 나중에 기록한 시점이 다르면 구분하며, 모르는 과거 시간을 만들어내지 않는다. 날짜만 확인되면 날짜와 시간 미확인을 적는다. 문서의 마지막 확인 시각을 과거 작업 시각으로 대체하지 않는다.

상태의 의미는 다음으로 제한한다.

- 계획: 작업 범위와 접근만 정리됨.
- 진행: 해당 범위의 작업이 진행 중임.
- 차단: 진행을 막는 조건과 해소에 필요한 입력이 있음.
- 검증 대기: 필요한 검증이나 사용자 확인이 남아 있음.
- 완료: 이 작업에 합의한 범위와 완료 기준을 충족함. 별도 배포까지 뜻하지 않음.

테스트 통과를 배포 완료로, 파일 수정을 커밋 완료로 확대 해석하지 않는다. 검증 근거에는 가능하면 파일 경로·실행 범위·확인 결과를 남긴다. 커밋을 인용할 때 미커밋 변경이 있으면 함께 표시하여 그 커밋만 검증한 것처럼 쓰지 않는다. 인증 정보나 비공개 원문 로그는 기록하지 않는다.

결정 기록은 제목, 상태(제안·채택·대체), 맥락, 선택, 이유, 주요 대안, 영향, 관련 작업 링크를 포함한다. 사소한 변경마다 만들지 않는다. 기존 결정을 뒤집으면 대체 관계를 남기고 과거 이유를 지우지 않는다.

## 문서 간 피드백

문서 간 피드백은 다음 순서로 닫는다.

1. 변경·검증 결과가 영향을 주는 목표, 구조, 결정, 작업 기록의 원본을 식별한다.
2. 승인 범위 안에서 해당 원본을 갱신한다. 실패한 검증은 작업 상태와 다음 행동에 되돌려 반영하고, 설계 변경이 필요하면 결정 검토로 연결한다.
3. 작업 기록에는 변경 이유와 원본 링크를 남긴다. 원본에는 향후 판단에 필요한 경우에만 관련 결정·작업 링크를 둔다. 모든 문서를 서로 연결하지 않는다.
4. 반영하지 못한 항목은 사유와 다음 행동을 남긴다. 관련 문서 갱신이 남아 있는데 기록 정합성까지 완료됐다고 표시하지 않는다.

예를 들어 기능 검증에서 설계의 가정이 틀린 것으로 확인되면, 검증 결과를 작업 기록에 남기고 상태를 재검토 대상으로 바꾼다. 승인된 수정 결정은 결정 원본에, 실제 수정된 흐름은 구조 원본에 반영하며 작업 기록은 두 원본을 참조한다. 같은 설명을 세 파일에 복사하지 않는다.

- 같은 사실은 한 원본에 두고 나머지 문서는 링크로 참조한다.
- 목표 변경은 목표 원본과 영향받는 활성 작업에, 구조 변경은 구조 원본과 관련 결정에 반영한다.
- 완료한 작업은 활성 목록에서 제외하되 필요한 이력과 링크는 보존한다.
- 오래된 기록과 현재 상태가 다르면 확인 범위와 정정 이유를 남긴다. 과거 수행 내용을 추정해 채우지 않는다.
- 깨진 링크나 원본 부재는 미해결 사항으로 표시한다. 찾지 못한 기록을 임의로 복원하지 않는다.
- 오래된 작업 기록의 보관·분리는 탐색 부담이 확인될 때 수행한다. v1에서 자동 삭제하지 않는다.
- 설치 재실행과 스킬 업데이트는 프로젝트 기록을 재생성하거나 덮어쓰지 않아야 한다.

사람은 기록 안내에서 활성 작업을 찾고, 작업 문서 상단에서 현재 단계를 확인하고, 변화 이력에서 시점·신규/변경 사항을 확인한 뒤 필요한 근거 링크만 따라갈 수 있어야 한다. 별도 종합 일지를 추가하기보다 이 경로를 먼저 유지한다.

## 실제 사용 확인

아래는 실제 사용에서 확인할 기준이며, 모두 통과했다는 기록이 아니다. 별도 시험 프로젝트에서 에이전트 결과와 실제 파일을 비교한다.

| 시나리오 | 기대 결과 |
|---|---|
| 신규 프로젝트에서 요구 일부가 미정 | 미정 사항을 사실로 채우지 않고 최소 기록만 생성 |
| 기존 프로젝트에 문서·이슈 체계 존재 | 원본을 재사용하고 중복 상태 파일을 만들지 않음 |
| 새 세션에서 진행 중 작업 재개 | 범위·미완료 항목·첫 행동을 실제 상태와 대조 |
| 기록에는 완료, 코드에는 미완료 | 차이를 드러내며 완료를 그대로 반복하지 않음 |
| 테스트 통과, npm 게시 미수행 | 검증과 게시 상태를 구분 |
| 다른 저장소 또는 브랜치로 이동 | 이전 기록을 무조건 적용하지 않고 범위 재확인 |
| 단순 질문 또는 오탈자 수정 | 불필요한 기록 파일을 추가하지 않음 |
| 읽기 전용 검토 요청 | 기록 갱신 명목으로 파일을 수정하지 않음 |
| 사용자 변경과 여러 작업이 공존 | 다른 작업 내용을 덮어쓰거나 완료로 처리하지 않음 |
| 초기화 재실행·스킬 갱신 | 기존 프로젝트 기록 내용 유지 |
| 링크 누락·기록 저장 실패 | 누락을 보고하고 성공으로 표시하지 않음 |

CLI 테스트는 파일 전달·보존을 검증한다. 에이전트가 올바르게 기억을 복원하는지는 별도 시나리오로 확인한다. 시험 전에 기대 사실과 완료 기준을 고정하고 실제 코드·명령 결과 및 사용자 검토와 비교한다. 에이전트 자신의 성공 선언만으로 통과시키지 않는다.

## 한계와 후속 작업

기록이 많아지면 링크 누락과 탐색 부담이 생길 수 있다. 실제 사용에서 복원 정확도와 중복 여부를 확인해 형식을 조정한다. 파일만으로 대규모 검색이나 동시 쓰기 충돌까지 해결한다고 가정하지 않는다.

지침을 설치해도 에이전트의 준수가 보장되지는 않는다. 대화 전체 저장, 모델 학습, 외부 서비스 동기화와 자동 Git 작업은 포함하지 않는다. 검색이나 외부 이슈 연계가 필요해지면 [시스템 전략](system-strategy.md)에 따라 소유권과 권한을 먼저 정한다.
